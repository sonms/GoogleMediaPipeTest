# GoogleMediaPipeTest 실기기 측정 결과

작성 기준일: 2026-10-06(2026-10-07에 10분 연속 측정 8.2절과 관련 항목을 추가). Android 실기기에서 측정한 결과와 그 한계를 정리한 기록입니다. iOS는 측정하지 않았습니다(iOS 미검증). 서버 스펙과 서버가 요구하는 입력이 정해지지 않았으므로, 이 문서는 "지금 수집 방식으로 어디까지 판단할 수 있는가"를 확인하는 용도입니다.

## 1. 요약

| 질문 | 현재 답 | 근거 수준 |
|---|---|---|
| 감정 데이터에 필요할 만한가 | 놀람과 웃음은 단순 분류기로도 구분됨. 화남, 역겨움, 슬픔은 약함. 일반화는 확인하지 못함 | 한 사람, 연기한 표정, 실질 근거 약 20개 구간 |
| 서버와 안정적으로 통신 가능한가 | 예측상 가능(양자화 바이너리 또는 JSON + gzip). 끊김과 재시도 같은 안정성은 판단 불가 | 실측 크기 + 가정한 네트워크 환산(예측만) |
| 어느 정도 리소스를 쓰는가 | 10분 연속에서 성능 저하와 메모리 증가 징후 없음, 식힌 상태에서 8fps로 10분 돌리면 온도 +6~7도(10분 시점에도 계속 상승, 상한 미확인), CPU 약 1.3코어분(제한 없이 돌리면 약 1.7코어분), 배터리 소모 시간당 약 33~39%(화면 켜짐 포함). 카메라 화면을 끄면 CPU -5%, 온도 상승 -0.8도로 효과는 작음(8.3절) | 한 기기, 최대 10분, 조건당 1회 |

## 2. 측정 환경

- 기기: Samsung Galaxy S8(SM-G950N), 전면 카메라. 세션 A~D는 USB 충전 중(디버깅 연결)에 측정했고, 세션 E와 F(10분 연속)는 무선 `adb`로 USB를 분리한 방전 상태에서 측정했습니다.
- 앱: `androidApp` debug 빌드, MediaPipe 0.10.21, 모델 `face_landmarker.task`, 얼굴 1개, 블렌드셰이프와 변환 행렬 출력 켬.
- 기록 설정: 소수 6자리, 단일 모드는 목표 30fps(실제 처리는 기기 한계).
- 자원 측정: `adb shell`의 `top`, `dumpsys battery`, `dumpsys meminfo`를 5초마다 수집(`.sessions/sample_device.sh`). 이 기기는 CPU 온도와 열 상태를 `adb`에 노출하지 않아서 발열은 배터리 온도로만 판단했습니다.

## 5. fps에 따른 결과

### 5.1 솎아 낸 데이터의 복원 오차 (세션 A, 이미 기록된 프레임에서 계산)

프레임을 일정 간격으로 솎은 뒤 선형 보간으로 복원했을 때의 오차입니다. 의미 있게 변하는 블렌드셰이프 33개 기준이며 값의 범위는 0~1입니다. 감정 분류 정확도가 아니라 정보 손실의 지표입니다.

| 실효 fps | 평균 오차 | 99% 오차 | 순간 최댓값 보존(평균 / 최악) |
|---|---|---|---|
| 8.7 | 0 | 0 | 100% / 100% |
| 4.3 | 0.0065 | 0.108 | 98% / 91% |
| 2.9 | 0.0105 | 0.155 | 96% / 81% |
| 2.2 | 0.0141 | 0.185 | 94% / 65% |

약 4fps까지는 손실이 작고, 3fps 이하에서는 빠르게 지나가는 표정(눈 깜빡임 등)의 최댓값이 19~35% 사라집니다. 솎아 낸 결과는 실제 저fps 입력과 다를 수 있습니다(MediaPipe의 추적 동작 때문).

### 5.2 비교 모드의 구조적 한계

비교 모드는 감지기 여러 개를 분석 스레드 하나에서 순차 실행합니다. 이 기기에서는 입력이 레인 수에 반비례해서 느려져서(세션 B는 3.1fps, 세션 C는 3.4fps), 목표 fps가 입력 속도보다 높은 레인은 모든 프레임을 처리해 서로 같은 데이터가 됩니다.

### 5.3 세션 B와 C

- **세션 B (30/10/5fps)**: 세 레인이 모두 같은 192프레임을 처리했고 10, 5fps 레인의 비교값이 완전히 같았습니다. 의미 있는 비교가 아닙니다.
- **세션 C (10/8/4/2fps)**: 10fps와 8fps 레인은 같은 223프레임을 처리했습니다. 실제로 비교된 것은 3.4, 2.7, 1.7fps 세 가지뿐입니다.

| 목표 fps | 처리 프레임 | 실효 fps | 기준 대비 블렌드셰이프 오차 | 랜드마크 변위 |
|---|---|---|---|---|
| 10 (기준) | 223 | 3.36 | 없음 | 없음 |
| 8 | 223 | 3.36 | 0.0005 | 0.00007 |
| 4 | 178 | 2.68 | 0.0024 | 0.00037 |
| 2 | 111 | 1.67 | 0.0072 | 0.0012 |

3.4fps에서 1.7fps로 절반이 되어도 블렌드셰이프 평균 오차가 0.7% 수준이므로, 정지와 완만한 변화는 낮은 fps에서도 유지됩니다.

## 6. 서버 전송 규모 예측 (예측만)

서버는 이 프로젝트의 범위가 아니므로 업로드 시간은 실측 크기를 가정한 네트워크 속도로 환산한 값입니다. 네트워크 프로파일: 열악 1Mbps/RTT 300ms, LTE 5Mbps/80ms, Wi-Fi 20Mbps/20ms, 프로토콜 오버헤드 10%. 크기는 얼굴이 잡힌 프레임 기준(세션 A)입니다.

| 형식 | 프레임당 | 분당 MB (8.7fps) | 1분 분량 업로드(열악 / LTE / Wi-Fi) | 인코딩 ms/프레임 |
|---|---|---|---|---|
| JSON 6자리 | 13.6KB | 7.1 | 62.8초 / 12.6초 / 3.1초 | 4.1 |
| JSON 4자리 | 10.6KB | 5.5 | 49.0초 / 9.8초 / 2.5초 | 4.1 |
| JSON 6 + gzip | 5.1KB | 2.7 | 23.8초 / 4.8초 / 1.2초 | 9.8 |
| JSON 4 + gzip | 3.2KB | 1.7 | 15.1초 / 3.0초 / 0.8초 | 8.4 |
| float32 바이너리 | 6.0KB | 3.1 | 27.9초 / 5.6초 / 1.4초 | 0.25 |
| 양자화 바이너리 | 3.0KB | 1.6 | 14.3초 / 2.9초 / 0.7초 | 0.28 |
| 양자화 + gzip | 2.9KB | 1.5 | 13.7초 / 2.8초 / 0.7초 | 0.90 |

- 용량은 fps에 비례합니다. 5fps라면 위 분당 값의 약 57%, 2fps라면 약 23%입니다.
- 열악한 네트워크에서 **원본 JSON 6자리만 1분 분량을 1분 안에 보내지 못합니다**. 나머지 형식은 여유가 있습니다.
- gzip은 JSON에서 효과가 크고(63% 감소), 양자화 바이너리에는 거의 없습니다(약 4%).
- 안정성(끊김, 재시도, 지연 변동, OS의 백그라운드 제약)은 서버와 전송 코드가 없어서 예측하지 못했습니다. 서버 연동 시점의 검증 항목으로 남깁니다.

## 7. 표정 구분 시험 (세션 D)

### 방법

- 무표정, 웃음, 슬픔, 화남, 놀람, 역겨움을 각 약 15초씩 지어 2라운드 반복했습니다(구간 사이 무표정 약 5초).
- 안내는 채팅으로 전달했고 안내 시각을 `.sessions/cues2.csv`에 기록했습니다. 폰과 PC의 시계 차이(약 12.7초)를 보정했습니다.
- 안내를 읽고 표정이 바뀌기까지의 지연을 약 5.5초로 추정해 구간을 잘랐습니다(웃음 구간의 변화 시점에서 추정).
- 블렌드셰이프 52개를 표준화해서 최근접 중심 분류기로 분류했습니다. 1라운드로 학습해서 2라운드로 검증하고, 반대로도 했습니다. 무표정이 구간의 약 1/3입니다. 기준선은 무작위 17%, 무조건 무표정 33%입니다.

### 결과

| 학습 → 검증 | 정확도 |
|---|---|
| 1라운드 → 2라운드 | 77% |
| 2라운드 → 1라운드 | 60% |

| 표정 | 정확도 | 주로 헷갈린 대상 |
|---|---|---|
| 놀람 | 95% | 거의 없음 |
| 웃음 | 79% | 슬픔 13% |
| 무표정 | 79% | 놀람 12% |
| 슬픔 | 58% | 화남 23%, 무표정 17% |
| 역겨움 | 47% | 무표정 50% |
| 화남 | 16% | 무표정 32%, 슬픔 27% |

구분에 기여한 값: 웃음은 `mouthSmileLeft/Right`, 놀람은 `jawOpen`과 `browInnerUp`/`browOuterUp`, 슬픔, 화남, 역겨움은 눈썹 바깥쪽 값의 감소와 눈 찡그림이 주였습니다.

### 해석과 한계

- 놀람과 웃음처럼 변화가 큰 표정은 단순 분류기로도 구분됩니다.
- 화남, 역겨움, 슬픔이 약한 이유가 데이터 때문인지 연기 때문인지는 구분할 수 없습니다.
- 한 사람이 일부러 지은 표정입니다. 자연스러운 감정과 다른 사람에게 통하는지 모릅니다.
- 같은 구간의 프레임은 서로 비슷하므로 근거는 프레임 수(약 2,600)가 아니라 약 20개 구간입니다. 정확도는 ±10%p 이상 흔들릴 수 있습니다.
- 전환 지연 보정을 3~8초로 바꾸면 2라운드→1라운드 정확도가 54~73%로 달라졌습니다. 방향성(놀람과 웃음이 잘 구분됨)은 모든 보정에서 같았습니다.
- 서버 AI는 이 분류기보다 강하고 시간 흐름도 쓸 수 있으므로 이 값은 참고용 하한에 가깝습니다.
- 세션 D의 전체 감지율 70%는 기록 초반 약 100초 동안 폰이 천장을 향해 있었던 영향이며 의미 있는 값이 아닙니다.

## 8. 기기 자원 사용

### 8.1 짧은 측정 (세션 C와 D, USB 충전 중)

| 항목 | 세션 C (비교 모드 1분) | 세션 D (단일 모드 4.4분) |
|---|---|---|
| 앱 CPU | 평균 169%, 최대 235% | 평균 182%, 109~213% |
| 메모리(PSS) | 평균 331MB (최대 356MB) | 184~205MB |
| 배터리 온도 | 35.1도에서 37.0도 | 35.3도에서 38.8도 |
| 감지 지연(평균 / p95) | 약 65ms / 약 125ms | 51ms / 76ms (얼굴 없는 구간 포함) |

- 세션 D의 온도 상승은 초반 30초에 +0.6도, 후반에는 30초에 +0.2도였습니다. 이 측정은 USB 충전 열이 더해진 값입니다.
- 메모리 값이 세션마다 달라서 하나의 값으로 정하지 못했습니다(앱 재시작 여부 등의 영향).
- 배터리 소모량은 USB 충전 중이어서 측정하지 못했습니다. 아래 8.2절에서 USB를 분리하고 측정했습니다.

### 8.2 10분 연속 측정 (세션 E와 F, USB 분리)

무선 `adb`(11절)로 USB를 분리한 방전 상태에서 측정했습니다. 단일 모드이고 비교 모드는 껐으며, 폰을 세워 두고 얼굴이 계속 카메라에 잡히게 했습니다. 화면 밝기는 같게 두었고 화면 켜짐을 유지했습니다. 두 세션 모두 자동 종료(10분)까지 기록했습니다.

| 항목 | E: 카메라 화면 켜짐 | F: 카메라 화면 꺼짐 | 차이 |
|---|---|---|---|
| 처리 속도 | 9.8fps (5,891프레임) | 13.0fps (7,813프레임) | +33% |
| 감지 지연(평균 / p95) | 60ms / 74ms | 51ms / 67ms | -15% |
| 앱 CPU 평균(범위) | 167% (135~203%) | 170% (47~259%) | 거의 같음 |
| 프레임당 CPU(CPU 평균 ÷ fps) | 17.0 | 13.1 | -23% |
| 배터리 온도(시작 → 종료) | 36.1 → 38.2도 (+2.1) | 35.6 → 38.2도 (+2.6) | 종료 온도 같음 |
| 온도 상승 속도(마지막 3분) | 0.12도/분 | 0.18도/분 | 둘 다 완만 |
| 배터리 소모(약 10.8분) | 78% → 71% (7%) | 70% → 64% (6%) | 정수 단위 한계로 비교 불가 |
| 방전 전류 평균(기기가 보고한 값) | 약 965 | 약 928 | 비슷함 |
| 메모리(PSS) 평균 / 최대 | 200 / 220MB | 222 / 240MB | +22MB |
| 감지율 | 99.9% | 95.7% | F가 낮음 |
| 분당 fps 범위 | 9.7~10.0 | 12.9~13.3 | 둘 다 안정 |

**결과**
- 10분 동안 분당 프레임 수가 일정해서 **발열로 인한 성능 저하(throttling)는 관찰되지 않았습니다.**
- 온도는 두 세션 모두 38.2도까지 올랐지만, 이 세션들은 따뜻한 상태(약 36도)에서 시작했습니다. 이 수치를 "38도에서 안정"으로 읽으면 안 됩니다. 식힌 상태에서 시작한 8.3절은 10분 동안 약 +6~7도 올랐고 마지막에도 0.35도/분 이상으로 계속 올랐으므로, 상한은 확인하지 못했습니다.
- 연속 사용 시 배터리 소모는 시간당 약 33~39%(화면 켜짐 포함)여서, 이 기기의 완충 기준으로 약 2.5~3시간입니다.
- **카메라 화면을 끄면 프레임당 비용이 줄었습니다**(프레임당 CPU -23%, 지연 -15%). 그러나 이 앱은 가능한 한 빠르게 처리하므로 줄어든 비용만큼 더 많은 프레임(+33%)을 처리했고, 그 결과 CPU와 종료 온도는 같았습니다. 같은 fps로 맞추면 화면을 끈 쪽이 더 시원할 것으로 예상하지만, 같은 fps로 비교하지 않았으므로 직접 확인한 결론이 아닙니다.

**한계**
- F는 시작 온도가 0.5도 낮았고, 화면에 얼굴이 보이지 않아 얼굴이 카메라에서 일부 벗어났는지 감지율이 95.7%였습니다. 얼굴이 없는 프레임은 연산이 가벼워서 속도 차이를 일부 키웠을 수 있습니다(4%대라서 33%를 설명하기에는 부족).
- E의 첫 온도 표본(38.1도)은 이전 사용의 잔열로 보여서 두 번째 표본(36.1도)을 시작 온도로 썼습니다.
- F의 메모리가 22MB 더 높았습니다. 계속 증가하는지는 확인하지 않았습니다.
- 두 세션 모두 앱의 화면이 켜져 있습니다. 화면을 끄거나 앱을 백그라운드로 보낸 구성은 측정하지 않았습니다. "카메라 화면 꺼짐"은 앱이 포그라운드에서 프리뷰와 오버레이만 그리지 않는 상태이며(요약 문구는 계속 갱신), 디스플레이 전력은 그대로 포함됩니다.

### 8.3 같은 fps(8fps)에서의 카메라 화면 켜짐과 꺼짐 (세션 G와 H)

8.2절은 fps가 달라서 직접 비교하지 못했으므로, 단일 모드를 8fps로 제한(`TARGET_FPS = 8`)하고 다시 측정했습니다. 두 세션 모두 USB 분리(무선 `adb`), 식힌 상태에서 시작, 같은 밝기와 폰 위치, 10분 자동 종료입니다.

| 항목 | G: 카메라 화면 켜짐 | H: 카메라 화면 꺼짐 | 차이 |
|---|---|---|---|
| 처리 속도 | 8.00fps (4,798프레임) | 7.99fps (4,792프레임) | 같음 |
| 배터리 온도(시작 → 종료) | 29.5 → 36.4도 (+6.9) | 28.3 → 34.4도 (+6.1) | -0.8도 (약 12%) |
| 온도 상승 속도(마지막 구간) | 0.35도/분 | 0.37도/분 | 같음 |
| 앱 CPU 평균(범위) | 131% (94~181%) | 125% (78~187%) | -5% |
| 프레임당 CPU | 16.4 | 15.6 | -5% |
| 방전 전류 평균(기기가 보고한 값) | 약 835 | 약 813 | -3% |
| 배터리 소모 | 55% → 49% | 41% → 35% | 둘 다 6% |
| 메모리(PSS) 평균 / 최대 | 201 / 219MB | 194 / 213MB | -7MB |
| 감지 지연(평균 / p95) | 60.7 / 84.7ms | 62.4 / 87.3ms | 차이 없음 |
| 감지율 | 99.9% | 99.4% | 차이 없음 |

**결과**
- 같은 일을 시켰을 때 카메라 화면을 끄면 CPU가 약 5%, 온도 상승이 약 0.8도 줄었습니다. 방향은 일관되지만 폭은 작습니다. 배터리 소모율은 같습니다.
- 발열과 CPU의 대부분은 감지 자체에서 나오고, 프리뷰와 오버레이 렌더링의 몫은 작습니다. 8.2절에서 화면을 끄자 처리량이 33% 늘어난 현상도 줄어든 렌더링 비용을 감지가 가져간 것으로 설명됩니다.
- 8fps로 제한하자 같은 기기에서 10fps 이상 제한 없이 돌릴 때(8.2절, CPU 약 170%)보다 CPU가 약 25% 낮았습니다. 처리 fps를 낮추는 것이 가장 큰 절감 수단입니다.

**한계**
- 각 조건을 한 번씩만 측정했고 시작 온도가 1.2도 달랐습니다. H가 더 식은 상태에서 시작해서 열이 더 쉽게 빠졌을 수 있으므로 실제 차이는 0.8도보다 약간 클 수 있습니다. 어느 쪽이든 폭이 작아서 단정하지 않습니다.
- 두 세션 모두 10분 시점에 온도가 계속 오르는 중이어서 더 긴 사용의 상한은 알 수 없습니다.
- 기록 시작 직전에 잘못 눌러 생긴 1.6초짜리 세션이 H의 파일에 섞여 있으며 분석에서 제외했습니다.

## 9. 측정 중 발견해서 고친 문제

| 문제 | 원인 | 조치 |
|---|---|---|
| 랜드마크 점이 얼굴과 어긋남 | MediaPipe가 랜드마크를 회전 전 센서 방향 기준으로 반환 | `Detectors.android.kt`에서 `rotationDegrees`만큼 x, y를 되돌림(코어는 항상 정립 기준 좌표를 반환) |
| 전면 카메라 오버레이 좌우 불일치 | 전면 프리뷰는 거울처럼 반전됨 | 앱 모듈이 `mirrorOverlay = true`로 오버레이를 반전 |
| 비교 모드가 fps 차이를 반영하지 않음 | 순차 실행으로 입력이 레인 목표보다 느려짐 | 5.2절. 구조 변경은 하지 않고 한계로 기록 |
| 안내 시각과 표정 전환의 어긋남 | 채팅 안내의 전달 지연 | 7절. 지연을 추정해 보정하고 민감도를 공개 |
| 카메라 화면을 없앨 수 없음 | 카메라 연결이 프리뷰 화면 생성에 묶여 있어서 화면을 없애면 분석도 멈춤 | `MainActivity`가 분석을 항상 연결하고 프리뷰 사용 사례는 화면이 보일 때만 연결. 화면에 "카메라 화면" 켜기/끄기 버튼 추가(기록 중에는 전환 불가) |
| 장시간 기록 중 화면이 꺼질 위험 | 화면 자동 꺼짐이 카메라를 멈출 수 있음 | `FLAG_KEEP_SCREEN_ON`을 설정 |
| 측정 스크립트의 시각이 어긋남 | 무선 `adb`는 호출마다 느려서 반복 횟수 기준의 시각이 실제와 달라짐 | `sample_device.sh`가 실제 경과 시간(`date`)으로 기록 |

회전 수정은 기록 파일의 좌표에도 영향을 줍니다. 세션 A~F는 모두 이 수정 이후에 기록했습니다.

## 11. 재현 방법

- 자원 측정: 기록 시작 직전이나 직후에 `sh .sessions/sample_device.sh <초> <출력.csv>` 실행(기기가 둘 이상이면 `ANDROID_SERIAL` 지정). 앱은 기록 버튼을 누르지 않아도 켜져 있는 동안 계속 감지하므로 기록 전부터 기기가 데워질 수 있습니다. 비교 측정 전에는 앱을 종료해서 시작 온도를 맞추세요.
- 무선 `adb`(USB 분리 측정): USB 연결 상태에서 `adb shell ip -f inet addr show wlan0`으로 폰의 IP 확인, `adb tcpip 5555`, `adb connect <IP>:5555`. 해제는 `adb disconnect`와 `adb usb`(또는 폰 재부팅). 인터넷은 필요 없지만 폰과 PC가 같은 서브넷에 있어야 하고, 클라이언트 격리가 켜진 망에서는 동작하지 않습니다. 열려 있는 동안 같은 망에서 접속을 시도할 수 있으므로 측정 후 닫습니다.
- 파일 회수: `adb pull /sdcard/Android/data/com.sonms.googlemediapipetest/files/ ./sessions`
- 표정 구간 분석: 세션의 `t`(기기 uptime)는 첫 프레임 기준 상대 시각으로 바꾸고, 안내 시각은 PC 시각에 `clock_offset_ms`를 더해 기기 시각으로 바꾼 뒤 기록 시작 시각(파일 이름의 epoch ms)을 빼서 맞춥니다.
