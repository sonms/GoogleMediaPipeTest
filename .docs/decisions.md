# GoogleMediaPipeTest 의사결정 기록

작성 기준일: 2026-10-02. 이 문서는 구조 설계 과정에서 확정한 결정과 그 이유를 정리한 기록입니다. 규칙 자체는 각 `CLAUDE.md`가 담당하고, 이 문서는 "왜 그렇게 정했는가"를 보존하는 용도입니다.

## 1. 프로젝트 목적과 범위

- Google MediaPipe를 Android와 iOS에서 함께 시험하는 KMP(Kotlin Multiplatform) 프로젝트입니다.
- 재사용 가능한 핵심부(`landmarkkit`)는 나중에 다른 Android 및 iOS 프로젝트에 의존성으로 배포될 수 있습니다. 다만 배포 여부는 아직 확정되지 않았으므로 틀만 잡는 단계입니다.
- 수집한 데이터는 서버에 구현될 감정 분석 AI의 학습 데이터로 쓰일 예정입니다. 감정 분석 자체와 서버는 이 프로젝트의 범위가 아닙니다.
- 이 앱이 증명해야 하는 것은 세 가지입니다: 데이터를 측정하고 수집할 수 있는가, 그 데이터가 유의미한가, 서버로 보내는 데 비용이 얼마나 드는가(예측만).

## 2. 용어

- **하네스**: 하네스 엔지니어링을 뜻합니다. `CLAUDE.md`, 훅, 설정, 스킬이 여기에 속합니다.
- **공통 모듈**: `shared`를 가리킵니다. 공통 Compose 화면이 있습니다.
- **앱 모듈**: `androidApp`과 `iosApp`을 가리킵니다. 카메라 코드가 있습니다.
- **코어**: `landmarkkit`을 가리킵니다. 배포 가능성이 있는 라이브러리입니다.

## 3. 구조 결정

| 번호 | 결정 | 이유 |
|---|---|---|
| 1 | 코어 모듈(`landmarkkit`)을 분리하고, 공통 모듈과 앱 모듈은 코어를 시험하는 연결 지점으로만 둔다. | 코어가 UI와 분리되어야 소비하는 프로젝트가 Compose 의존성을 떠안지 않는다. |
| 2 | 배포 범위는 추론 코어까지다. 카메라(CameraX, AVCaptureSession)는 앱 모듈에만 둔다. | 소비하는 앱이 자체 카메라 파이프라인을 가질 가능성이 높고, 카메라를 포함하면 권한과 생명주기 책임이 커진다. |
| 3 | 초기에는 로컬 소비(`mavenLocal`, 로컬 포드)로 검증하고, 원격 배포는 API가 굳은 뒤에 한다. | API가 자주 바뀌는 단계에서 배포 인프라를 만들면 낭비다. |
| 4 | CLAUDE.md와 훅을 모두 만들되, 규칙을 먼저 확정하고 훅은 나중에 추가한다. | 규칙이 바뀔 때마다 훅을 고치는 비용을 피한다. |
| 5 | 공개 API는 `commonMain`의 인터페이스와 데이터 타입이고, 플랫폼 구현체는 `internal`이다. | 외부 소비자에게 변경에 강한 경계를 제공하고, 가짜 구현으로 교체할 수 있다. |
| 6 | 입력은 공통 `Frame` 타입이고, 플랫폼별 변환 함수(Android `Bitmap.toFrame`, iOS `CMSampleBufferRef.toFrame`)를 코어가 제공한다. | 프레임 복사를 피해 지연을 줄인다. 코어가 CameraX에 의존하지 않도록 Android는 `Bitmap`을 받는다. |
| 7 | 초기 구현은 Face만 하고, Hand는 타입과 인터페이스 경계만 둔다. | 한 가지를 양쪽 플랫폼에서 끝까지 검증하면 이후 태스크는 같은 패턴으로 확장할 수 있다. |
| 8 | 모델 파일(`.task`)은 소비자가 준비해서 경로로 전달한다. 코어는 번들하거나 다운로드하지 않는다. | 코어에 네트워크와 저장 코드가 들어가지 않고, 라이브러리 용량이 작아진다. |
| 9 | 이름은 `LandmarkKit`이다(모듈 `landmarkkit`, 패키지 `com.sonms.landmarkkit`, iOS 프레임워크 `LandmarkKit`). | "MediaPipe"를 이름에 쓰면 공식 라이브러리로 오해받고 상표 문제가 생길 수 있다. 검색 기준으로 충돌은 없었으나 배포 전에 재확인한다. |
| 10 | 카메라는 각 앱 모듈에 두고, 공통 모듈은 화면만 담당한다. | iOS 카메라를 Swift로 쓰는 편이 안정적이고, 격리 규칙이 단순하다. |
| 11 | iOS에서는 코어의 `iosMain`이 Kotlin cinterop으로 MediaPipe 포드를 직접 호출한다. 기술적으로 막히면 협의 후 Swift 구현 주입 방식으로 전환한다. | 두 플랫폼이 같은 인터페이스를 구현해야 배포 목적에 맞는다. |
| 12 | CLAUDE.md는 루트와 모듈별로 나눈다. 영어로 작성하고 응답은 한국어로 한다. | 모듈별 규칙만 해당 작업 시 로드되어 지켜질 가능성이 높다. |
| 13 | iOS는 Windows에서 검증할 수 없으므로 "iOS 미검증"을 명시하고 Mac에서 실행할 명령을 남긴다. Mac과 CI 사용 여부는 미정이다. | 검증하지 못한 부분을 검증한 것처럼 보고하는 일을 규칙으로 막는다. |
| 14 | 코어 의존성은 최소로 제한한다(Compose, 네트워크, DI, 알파 버전 금지). 새 의존성은 승인 후 추가한다. 버전은 `libs.versions.toml`에서만 관리한다. MediaPipe 버전은 고정한다. | 코어의 의존성은 소비하는 앱에 전파된다. |
| 15 | Git 규칙은 아직 정하지 않았고, 커밋과 푸시는 요청이 있을 때만 한다. | 사용자 지시. |

## 4. 데이터와 측정 결정

| 번호 | 결정 | 이유 |
|---|---|---|
| 16 | 코어는 MediaPipe가 주는 모든 값을 노출한다. 얼굴 단위 `Face`에 랜드마크 478개, 블렌드셰이프 52개, 4×4 변환 행렬을 담고, 설정 플래그로 출력을 켜고 끈다. 신뢰도 임계값도 모두 노출한다. | 학습에 어떤 특징량이 유효한지 아직 모르므로 코어는 정보를 잃지 않아야 한다. |
| 17 | 라벨링은 하지 않는다. 감정 분석은 서버 AI가 담당한다. | 앱의 책임은 수집 가능성, 유의미성, 전달 비용 예측까지다. |
| 18 | 서버, 모의 서버, 업로더, 청크 큐는 만들지 않는다. KMP 안에서 실측한 값을 가정한 네트워크 속도로 환산해 예측만 한다. | 사용자 지시. 서버는 별도 작업이다. |
| 19 | 데이터 유의미성은 대리 지표로 판단한다: 감지 성공률, 블렌드셰이프 변동폭, 떨림, 처리 지연과 누락 프레임, 전송 용량. | 라벨이 없을 때 수집 품질을 즉시 확인할 수 있는 방법이다. |
| 20 | 기록은 앱 안의 로컬 세션 레코더로 한다. 기본값은 10fps, JSONL + gzip, 세션당 최대 10분이고, 모든 값은 설정으로 바꿀 수 있다. | 용량 부담을 줄이고 형식 결정을 실험 결과 이후로 미룬다. |
| 21 | fps 비교는 같은 카메라 스트림에 30, 10, 5fps 감지기 3개를 병렬 실행하는 비교 모드로 한다. 간격은 타임스탬프 기준이다. | 30fps 기록을 솎아낸 결과는 MediaPipe의 추적 동작 때문에 실제 저fps 결과와 다를 수 있다. 입력이 같아야 짝지어 비교할 수 있다. |
| 22 | 보고서는 형식 7종(JSON 6자리, JSON 4자리, 각각 gzip 적용, float32 바이너리, 양자화 바이너리, 양자화 + gzip)과 네트워크 프로파일 3종(열악 1Mbps/RTT 300ms, LTE 5Mbps/80ms, Wi-Fi 20Mbps/20ms, 프로토콜 오버헤드 10%)으로 만든다. | 사용자 승인. gzip 압축 효과 확인이 핵심 질문이다. |
| 23 | gzip 측정은 Okio를 공통 모듈에만 추가해서 한다(코어에는 추가하지 않는다). | Kotlin 표준 라이브러리에는 압축이 없다. 코어 의존성 규칙과 충돌하지 않는다. |
| 24 | JSON은 직접 작성한 최소 작성기로 만든다. 프레임 줄에는 블렌드셰이프 점수만 쓰고, 이름 목록은 `<세션ID>.report.json`의 `quality.blendshapes`에 기록한다(헤더는 첫 프레임 전에 써야 하는데 이름은 첫 결과가 나와야 알 수 있기 때문). | 숫자 배열과 단순 객체만 필요하고, 자릿수를 직접 통제할 수 있으며, 서버 스키마가 정해지지 않아 바꾸기 쉬워야 한다. |
| 25 | 소수 자릿수는 설정값이고 기본 6자리다. 보고서에는 4자리 변형도 함께 측정한다. | 원본 정밀도를 보존하면서 절약 효과를 같은 데이터로 계산한다. |
| 26 | 양자화는 x, y를 `uint16`, z를 `int16`(범위 ±0.5, 초과 시 자르고 횟수 기록), 블렌드셰이프를 `uint16`, 변환 행렬은 float32로 한다. 얼굴 1개 기준 약 3.0 KB다. | 8비트는 좌표 해상도가 거칠다. z 범위는 가정이므로 실측 최솟값과 최댓값으로 검증한다. |
| 27 | 기록 파일은 앱 전용 저장소에 저장한다(Android `getExternalFilesDir`, iOS Documents). `adb pull`이나 Files 앱으로 꺼낸다. 공유 버튼은 만들지 않는다. | 추가 의존성과 UI가 필요 없다. |
| 28 | 세션 제어는 공통 Compose 화면의 시작과 종료 버튼으로 한다. 종료하면 화면에는 "종료되었습니다"만 표시하고, 메타데이터와 보고서는 파일로 기록한다(`<세션ID>.jsonl`의 첫 줄에 메타데이터, `<세션ID>.report.json`에 보고서). 10분 상한에 도달하면 자동 종료한다. (2026-10-02 수정: 보고서 화면 표시는 제외) | 두 플랫폼이 같은 UI와 동작을 공유한다. 보고서는 PC로 꺼내서 분석하므로 화면 표시가 필요 없다. |
| 29 | 떨림은 정지 구간(변환 행렬의 이동량과 회전량 변화가 임계값 이하)에서만 프레임 간 평균 변위의 중앙값으로 계산하고, 초당 변위도 함께 표시한다. 정지 구간이 없으면 "측정 불가"로 표기한다. | 얼굴의 실제 움직임과 노이즈를 구분하고, fps가 다른 결과를 비교할 수 있게 한다. |
| 30 | 세션 메타데이터는 환경, 모델과 설정, 입력, 기록 설정, 세션 ID와 시각을 기록하고, 개인 식별 정보(기기 고유 ID, 광고 ID, 위치 등)는 제외한다. | 재현성은 확보하되 얼굴 좌표가 생체 정보이므로 식별 수준을 최소화한다. |
| 31 | 테스트는 계산 로직만 `commonTest`로 검증한다(양자화 오차, 클램프 횟수, JSON 형식, 바이트 크기, 떨림 계산). | 측정 도구의 계산 오류는 결과가 그럴듯해 보여서 발견하기 어렵다. |

### 구현 중에 추가로 정한 사항

| 번호 | 결정 | 이유 |
|---|---|---|
| 32 | 병렬 비교 레인의 목록은 `CompareFps` 상수 한 곳에서 바꾸고, 첫 레인이 기준(baseline)이다. 처음에는 30, 10, 5fps였고, 2026-10-06에 10, 8, 4, 2fps로 바꿨다. | fps 목록이 바뀌어도 되도록 하라는 요구. 테스트 기기(Galaxy S8)가 30fps를 처리하지 못해서 기준 레인이 성립하지 않았다. |
| 33 | 레인의 처리 여부는 타임스탬프 간격으로 판단한다(목표 간격에서 카메라 프레임 반 개, 약 16 ms를 뺀 값 이상 경과했을 때). | 카메라 프레임이 불규칙하게 도착해도 목표 fps에 가깝게 유지한다. |
| 34 | 레인마다 기록 파일(`.jsonl`)과 보고서(`.report.json`)를 따로 쓰고, 세션 전체에 대해 `.compare.json`을 추가로 쓴다. 비교값은 기준 레인과 같은 입력 프레임에서 짝지어 계산한다(감지 일치 및 불일치 횟수, 블렌드셰이프 평균 절대 차이, 랜드마크 평균 변위). | 사후 솎아내기가 아니라 실제 저fps 입력에서의 차이를 측정하기 위해서. |
| 35 | 비교 모드는 기록 시작 전에만 켜고 끌 수 있다. 꺼져 있으면 감지기 1개로 동작한다. | 세션 중간에 구성이 바뀌면 비교가 성립하지 않는다. |
| 36 | 떨림의 정지 구간 판별은 변환 행렬 배치(행 우선 또는 열 우선)를 가정하지 않고, 아핀 행(0,0,0,1)의 위치로 자동 판별한다. 임계값은 `STILL_TRANSLATION`(0.5)과 `STILL_ROTATION`(0.01) 상수다. | MediaPipe가 반환하는 행렬 배치를 확인하지 못했다. 임계값은 실측으로 조정한다. |
| 37 | 파일 이름은 `<시작시각 epoch ms>_<세션ID>`로 시작하고, 세션 ID는 무작위 16진수다. | 정렬이 쉽고 개인 식별 정보가 들어가지 않는다. |
| 38 | iOS 모델 로딩 경로는 앱 번들 안의 `face_landmarker.task`이고, Android는 assets 이름이다. 두 앱 모듈이 같은 테스트 모델을 각자 보유한다. | 결정 8(소비자가 준비해서 경로로 전달)의 적용. |

## 5. 서버 전송 규모 이론 추정 (실측 전)

얼굴 1개, 프레임 1장 기준이며 MediaPipe Face Landmarker 출력 구성을 바탕으로 한 이론값입니다. 실측값은 측정 기능 구현 후 보고서가 대체합니다.

| 구성 | 크기 |
|---|---|
| 랜드마크 478개 JSON(6자리) | 약 21 KB |
| 랜드마크 478개 float32 바이너리 | 약 5.7 KB |
| 양자화 바이너리(랜드마크, 블렌드셰이프) | 약 3 KB |
| 블렌드셰이프 52개 float32 | 약 0.2 KB |

30fps로 연속 전송 시: 랜드마크 JSON은 약 5 Mbps(1시간 약 2.3 GB), 바이너리는 약 1.4 Mbps(1시간 약 0.6 GB), 블렌드셰이프와 행렬만 보내면 약 0.07 Mbps(1시간 약 29 MB)입니다.

| 세션 레코더(시작과 종료 버튼, 종료 안내 텍스트), 메타데이터와 보고서 파일 저장 | Android 구현 및 빌드 성공, 실기기 실행 미확인. iOS는 작성만 하고 미검증. 보고서 화면 표시는 범위에서 제외 |
| 병렬 감지기 비교(순서 ④): 레인별 기록, 기준 레인과의 짝 비교(`*.compare.json`) | Android 구현 및 빌드 성공, 로직 테스트 통과(합성 데이터), 실기기 실행 확인. 단, 순차 실행 구조라서 이 기기에서는 입력이 레인 목표보다 느려져 8~10fps 비교가 성립하지 않음(`measurements.md` 5절). iOS는 작성만 하고 미검증 |
| Android 실기기 측정(전면 카메라, 표정 시나리오, 자원) | 완료. 결과는 `measurements.md` 참고. 서버 스펙이 정해지기 전까지 추가 검증은 하지 않기로 함 |

구현 순서는 ①직렬화와 크기 측정 → ②예측 보고서 → ③품질 지표 → ④병렬 감지기 비교입니다.

## 8. 알려진 위험과 한계

- **변환 행렬 배치 미확인**: MediaPipe가 반환하는 4×4 행렬이 행 우선인지 열 우선인지 확인하지 못했습니다. 떨림 계산은 아핀 행(0,0,0,1)의 위치로 배치를 자동 판별하지만, 실기기 데이터로 검증이 필요합니다.
- **기록 시 이중 인코딩**: 레코더가 프레임 줄을 쓰고 측정기가 같은 프레임을 다시 인코딩합니다. 분석 스레드 부하가 늘 수 있으며, 감지 지연(`latency`)은 감지 호출만 재므로 영향을 받지 않습니다.

- **iOS 미검증**: cinterop 이름(`MPPFaceLandmarker`, `MPPTransformMatrix` 등)과 Swift 쪽 이름이 추정에 기반해서 Mac에서 수정이 필요할 가능성이 높습니다.
- **MediaPipe 버전**: Android와 iOS 모두 0.10.21로 고정했습니다. iOS 포드 0.10.33 이상에서 링크 문제가 보고되어 있습니다.
- **CocoaPods 플러그인**: Kotlin CocoaPods 플러그인은 유지보수 모드이므로, 장기적으로 Swift Package Manager 연동으로 옮겨야 할 수 있습니다.
- **개인정보**: 얼굴 좌표는 생체 정보로 분류될 수 있으므로, 서버 연동 전에 동의와 익명화 정책이 필요합니다.
- **블렌드셰이프의 한계**: 정답이 아니라 MediaPipe 모델의 추정값이므로 모델이 바뀌면 분포가 달라질 수 있습니다.
- **오버레이 정렬**: 3:4 영역 일치를 전제로 합니다. Android는 전면 카메라를 쓰며 `mirrorOverlay`로 좌우 반전을 처리했습니다(실기기 확인). iOS는 처리하지 않았습니다.
- **랜드마크 회전**: Android MediaPipe는 랜드마크를 회전 전 센서 방향 기준으로 돌려주므로 코어에서 `rotationDegrees`만큼 되돌립니다(실기기 확인). iOS의 같은 문제 여부는 확인하지 못했습니다(iOS 미검증).
- **백그라운드 전송**: 실제 서버 연동 시 OS의 백그라운드 제약 때문에 플랫폼별 전송 장치(WorkManager, BGTaskScheduler)가 필요합니다.
